## 1. 核心问题

当前 AI 购物助手通常采用**工具中介式（tool-mediated）架构**：LLM 负责意图理解、对话管理、规划和解释，而商品空间的检索、排序、推荐由外部工具完成。这种分工存在严重的**接口信息损失（interface loss）**问题——复杂、细粒度的购物上下文（多轮偏好、场景约束、反馈信号）必须被压缩为紧凑的工具调用输入，导致大量信息在传递过程中丢失，特别是在多轮交互场景下。

## 2. ShopX 核心方案

ShopX 是一个**模型原生履约（model-native fulfillment）**的基础模型，将意图理解、执行规划和 SID 原生的商品空间操作统一到一个模型中：

### 2.1 关键能力
- **商品空间操作**：SID 束搜索检索、列表排序、商品组合/捆绑
- **商品锚定响应**：生成商品锚定的摘要、对比、推荐列表、文本-SID 交织回答
- **交互与状态更新**：主动追问澄清、反馈融入、偏好记忆更新

### 2.2 模型-Harness 边界
ShopX 通过一个**轻量级 Serving Harness** 部署，定义四槽位动作协议：

| 动作槽位 | 职责 |
|---------|------|
| **Plan** | 意图理解、证据需求判断、履约路径规划 |
| **Execute** | SID 原生商品空间操作（检索、重排、组合） |
| **Fulfill** | 商品锚定的用户响应生成 |
| **Update** | 偏好摘要、记忆更新信号输出 |

Harness 提供三类支撑面：**Context**（用户画像/行为）、**Catalog**（SID 验证与商品证据）、**State**（跨轮状态管理）。

### 2.3 三种服务模式
1. **意图到商品履约**：明确的购物请求 → 检索+排序 → 锚定响应
2. **上下文增强个性化**：模糊/上下文驱动的请求 → 先拉取用户画像/行为 → 再履约
3. **有状态多轮履约**：跟进式请求 → 读取历史状态 → 修订/扩展 → 写回状态更新

## 3. Semantic ID 设计

### 3.1 设计目标
- **语义可恢复性（Recoverability）**：SID 应保留商品语义信息（类别、属性、风格等）
- **LLM 可操作性（LLM Operability）**：SID 应适合自回归生成，前缀结构稳定

### 3.2 多模态商品表示
- 使用 **Qwen3-VL-Embedding-2B** 作为编码器，替代传统的分散式模态编码（CLIP+BERT+Q-Former）
- 采用**等价商品监督（Equivalent-Product Supervision）**替代协同过滤信号，确保语义对齐
- 引入 **Soft-target InfoNCE** 损失，对同类但不同的商品赋予软负样本权重
- 支持**单向量（SV）和多向量（MV）**输出结构

### 3.3 混合全局-局部 SID（G₂+L₄）
- **Global Prefix（G₂）**：通过残差量化（RQ）从全局嵌入生成 2 个前缀 Token，保证生成稳定性
- **Local Suffix（L₄）**：通过 VQ 从 4 个局部嵌入生成后缀 Token，保留细粒度属性信息
- 每个码本级 8192 个码字，共 6×8192 个新 SID Token
- G₂ 支持稳定的自回归生成路由，L₄ 提升语义可恢复性

## 4. 训练方案

### 4.1 整体流程
```
SID Token Alignment → Domain CPT → SFT → Specialist Preparation → OPD-RL Joint
```

### 4.2 SID Token 对齐
- 冻结基座模型，仅训练新增 SID Token Embedding
- 使用商品到 SID 和 SID 到商品的重构数据
- 200B Token，1 epoch，仅更新 Embedding 层

### 4.3 领域持续预训练（Domain CPT）
- **数据配比**：70B 电商域 Token + 35B 通用回放 Token（2:1 比例）
- **电商域数据**：目录-SID 锚定、意图/行为到商品锚定、用户偏好理解
- **通用回放数据**：知识推理、指令遵循、数学编程（防止灾难性遗忘）
- 全参数训练，上下文长度 20,480 Token

### 4.4 监督微调（SFT）
- 通用数据占 81.2%（保持指令遵循、工具使用等能力）
- 购物数据占 18.8%（SID 履约、用户/上下文理解、对话监督）
- 上下文长度 81,920 Token

### 4.5 OPD-RL 联合训练
SFT 存在三个缺陷：SID 预测不够深、通用能力可能退化、排序/交织响应缺乏结果级反馈。

**五任务族路由**：

| 任务族 | OPD 教师 | RL 奖励 |
|--------|----------|---------|
| General | 通用教师（预对齐基座） | LLM Judge |
| SID Prediction | SID 预测教师 | 无（稀疏奖励无效） |
| Ranking | 无 | NDCG 奖励 |
| Interleave | 无 | 交织履约奖励 |
| Other | 自教师（冻结 SFT） | 无 |

**MOPD（多教师在线策略蒸馏）**：用教师-学生对数概率比作为 Token 级偏好权重

**奖励设计**：
- **LLM Judge**：0-10 分语义评估
- **Ranking Reward**：NDCG 基础排序奖励
- **Interleaved Fulfillment Reward**：规则有效性检查 + 层级 SID 匹配 + 目录锚定的裁判分数

## 6. 实验评估

### 6.1 评估协议
- **框架级评估**：279 个单轮案例 + 80 个多轮轨迹，源自匿名化淘宝生产日志
- **能力分解评估**：通用能力（MMLU-Pro, CMMLU, IFEval, BBH, GPQA, MATH, GSM8K, MBPP+）+ 购物诊断（购物语义、上下文证据提取、文本化推荐/搜索、商品空间履约）

### 6.2 框架级结果
- ShopX 在**商品精确度、排序质量、约束锚定、反馈适应、跨轮引用**上优于工具中介式基线
- 工具中介式基线（InteRecAgent, Chat-REC, RecMind 风格）在首轮匹配上仍有竞争力
- ShopX 优势集中在**状态需要跨轮保持一致**的场景
- 关键洞察：模型原生履约减少了语言理解与商品空间执行之间的有损转接

### 6.3 能力分解结果
- 领域训练后 GPQA-Diamond 从 47.5 降至 41.4，MATH-500 从 76.2 降至 59.6（领域专业化的代价）
- G₂+L₄ SID 相比 FORGE SID 在个性化序列推荐上 HR@4 从 2.8 提升至 7.1，意图+历史检索从 5.6 提升至 13.1
- 4B → 8B 扩展普遍提升，但部分诊断不单调

### 6.4 消融实验关键发现

**SID 设计**：
- 等价商品监督优于协同过滤监督（语义对齐更强）
- G₂+L₄ 在保持可操作前缀的同时，通过局部后缀提升商品特异性
- 重建损失训练能编码更多可恢复的多模态信息

**CPT 数据配比**：
- SID 对齐是 CPT 的前提条件（未对齐的 CPT 检索性能差）
- 2:1 的域-通用 Token 比例在商品检索和通用能力之间取得最佳平衡

**后训练管线**：
- SID 预测教师单独使用会严重退化通用能力（Profile Extraction 和 Ranking 降至 0）
- **MOPD-3T**（通用教师 + SID 教师 + 自教师）实现了 SID 专业化与通用能力的最优平衡
- 完整的 OPD-RL 联合训练达到最佳结果：Ranking 70.1，Text-SID 88.0

## 6. 相关工作定位

- **工具中介式推荐**：ShopX 提供了替代范式，模型直接操作商品空间而非通过工具接口
- **后检索 LLM 重排序**（如 RankGPT）：ShopX 覆盖完整履约链路，而非仅重排已有候选集
- **生成式推荐与 SID**（TIGER, OneRec 系列）：ShopX 将 SID 从"候选生成器"提升为"模型操作的商品语言"

---

## 7. 讨论与未来方向

- **模型原生履约作为新的服务锚点**：不是替代检索索引和排序模型，而是改变复杂上下文在履约流程中的承载方式
- **走向 Agentic 训练**：当前训练不含面向完整购物轨迹的强化学习，未来应引入轨迹级 RL 和多轮模型-Harness 交互优化
- **动态用户模拟器**：可作为个性化 Agentic RL 的交互式奖励信号源

---

## 8. 总结

ShopX 提出并验证了模型原生履约这一新范式，核心贡献在于：
1. 统一意图理解、执行规划与 SID 原生商品空间操作到一个基础模型
2. 设计的混合全局-局部 SID（G₂+L₄）兼顾了 LLM 可操作性和语义可恢复性
3. 完整训练管线（对齐 → CPT → SFT → MOPD → RL）在保持通用能力的同时实现商品空间专业化
4. 在淘宝规模的生产环境数据上验证了框架有效性

## 10. 讨论记录

### 10.1 以一个例子说明线上实际如何运行

**场景设定**：用户是一位热爱骑行的城市通勤者，想要为夏季骑行准备一套装备。

**第一轮交互：意图到商品履约**

用户："夏天骑车太热了，想买点凉快的骑行装备"

- **Plan**：识别出购物意图但信息不够具体，决定先追问澄清
- **澄清**：用户补充"城市通勤，预算500元左右，想要上衣和手套"
- **Plan（重新规划）**：识别多类别捆绑需求，执行 SID 束搜索检索
- **Execute**：生成"夏季骑行上衣"和"骑行手套"的 SID 候选，调用 Catalog 验证并获取商品证据，进行重排筛选
- **Fulfill**：生成自然语言响应，嵌入 SID，展示推荐商品
- **Update**：写入用户偏好（夏季骑行、城市通勤、预算500元、简约风格）到 State

**第二轮交互：有状态多轮履约**

用户："手套想要长指的，另外有没有头盔推荐？"

- **Plan**：读取 State 历史信息，识别修改手套约束+新增头盔需求
- **Execute**：修订手套候选集为长指，扩展新类别执行头盔 SID 检索
- **Fulfill**：输出更新后的推荐列表
- **Update**：更新偏好记忆（手套偏好长指、新增头盔需求）

**第三轮交互：最终确认与购买**

用户："就这套吧，帮我下单"

- **Plan**：确认用户意图，准备生成最终订单
- **Execute**：从 State 提取所有选定商品，生成完整订单信息
- **Fulfill**：输出最终订单汇总
- **Update**：写入最终状态，标记会话完成

**核心机制总结**：

| 组件 | 职责 | 在示例中的体现 |
|------|------|----------------|
| **Plan** | 意图理解、证据需求判断、履约路径规划 | 识别多类别需求、读取历史状态、规划修订/扩展路径 |
| **Execute** | SID 原生商品空间操作 | 执行 SID 束搜索检索、重排、捆绑组合、调用 Catalog 验证 |
| **Fulfill** | 商品锚定的用户响应生成 | 生成自然语言响应，嵌入 SID，展示商品信息和推荐理由 |
| **Update** | 偏好摘要、记忆更新信号输出 | 写入用户偏好、已展示商品、会话进度到 State |
| **Context** | 用户画像/行为 | 拉取历史购买记录，了解用户风格偏好 |
| **Catalog** | SID 验证与商品证据 | 将模型生成的 SID 解析为真实商品信息 |
| **State** | 跨轮状态管理 | 保存用户偏好、已展示商品，支持多轮跟踪 |

**与工具中介式架构对比**：传统架构每轮需要"LLM→生成查询→调用搜索工具→解析结果"，状态容易在接口转换中丢失；而 ShopX 直接在模型内部操作商品空间（SID），状态在模型和 Harness 之间流转，减少了接口信息损失。

### 10.2 LLM 具体如何进行 SID 束搜索检索

**1. SID 的本质：商品的离散语言表示**

SID 不是传统商品 ID，而是将商品多模态信息（图片、标题、属性）压缩为短 token 序列的离散化语义编码，适合 LLM 自回归生成。

**2. SID 的结构设计：G₂+L₄**

```
SID = [z^G_1, z^G_2] + [z^L_1, z^L_2, z^L_3, z^L_4]
       ↑ 全局前缀(2个)     ↑ 局部后缀(4个)
```

| 部分 | 生成方式 | 作用 |
|------|----------|------|
| **Global Prefix (G₂)** | 残差量化（RQ） | 提供稳定的自回归生成路由 |
| **Local Suffix (L₄)** | 向量量化（VQ） | 保留细粒度属性信息（颜色、材质、功能等） |

每个码本级有 **8192 个码字**，总共可表示 $8192^6 \approx 3 \times 10^{22}$ 种语义组合。

**3. 自回归束搜索生成过程**

以"夏季骑行上衣"为例：

```
用户意图 → "夏季骑行上衣，透气，简约风格"

生成步骤：
Step 1: 生成 z^G_1 (全局前缀第1级) → [1024] (骑行装备大类)
Step 2: 生成 z^G_2 (全局前缀第2级) → [2048] (骑行上衣子类)
Step 3: 生成 z^L_1 (局部后缀第1级 - 季节) → [100] (夏季)
Step 4: 生成 z^L_2 (局部后缀第2级 - 材质) → [200] (冰丝面料)
Step 5: 生成 z^L_3 (局部后缀第3级 - 功能) → [500] (透气)
Step 6: 生成 z^L_4 (局部后缀第4级 - 风格) → [1000] (简约风格)

最终生成的 SID: [1024, 2048, 100, 200, 500, 1000]
```

**4. 束搜索策略：Progressive Beam-Size Schedule**

论文使用 `[8, 32, 64, 64, ...]` 的渐进式束搜索：
- 生成第 1 级 token 时，保留 top-8 个候选
- 生成第 2 级 token 时，扩展到 top-32 个候选
- 生成第 3 级及以后时，保留 top-64 个候选
- 最终返回最多 **64 个生成的 SID**

**5. SID 与 Catalog 的交互**

生成 SID 候选后，通过 Catalog 进行验证：

```
LLM生成SID候选 → SID验证(Catalog) → 商品证据(真实商品)
                      │
                      ├─ 验证SID有效性
                      ├─ 解析为商品ID
                      └─ 查询商品详情(标题/图片/价格)
```

**6. 无效 SID 处理**

论文明确指出："We do not use constrained decoding or illegal-SID filtering, so invalid SID strings are counted as failed resolutions." 无效的 SID 会被视为解析失败，直接丢弃。

**7. 为什么使用束搜索而不是贪心搜索？**

- 贪心搜索只保留每个步骤的最优选择，可能陷入局部最优
- 束搜索保留多个候选路径，在后续步骤中可以发现更好的组合
- 对于商品检索，多样性比单一最优更重要

### 10.3 检索过程是否依赖 LLM

**核心结论：是的，这个检索过程完全依赖 LLM，不能通过确定性的方式直接索引。**

**1. 关键区别：自回归生成 vs 确定性索引**

| 维度 | 传统确定性索引 | ShopX SID 自回归生成 |
|------|----------------|----------------------|
| **输入** | 关键词/向量 | 用户意图（自然语言） |
| **过程** | 查询 → 匹配 → 返回 | 理解 → 生成 → 验证 |
| **确定性** | 相同输入总是返回相同结果 | 相同输入可能返回不同候选（束搜索） |
| **语义理解** | 依赖索引构建时的语义编码 | 模型直接理解用户意图 |
| **灵活性** | 受索引结构限制 | 可以生成全新的 SID 组合 |

**2. 为什么不能用确定性索引？**

- **用户意图是自然语言**：用户说"夏天骑车太热了，想买点凉快的骑行装备"，这是模糊的自然语言，不是结构化查询，需要 LLM 先理解
- **SID 的生成是语义推理过程**：层级之间的选择不是简单的查表，而是通过训练学习到的映射关系
- **多意图处理需要综合推理**：用户同时要"上衣"和"手套"，模型需要识别两个独立需求，为每个类别生成对应的 SID，并考虑搭配和预算约束
- **上下文和历史状态需要融入**：多轮对话中，模型需要记住用户偏好、历史购买记录，理解当前请求与之前对话的关系

**3. 论文中的证据**

- **摘要**："We unify intent understanding, execution planning, and SID-native item-space operations into a single foundation model."
- **核心方案**："The model fills these slots by inspecting the current request, deciding what evidence is needed, determining how the intent should be grounded in the item space..."
- **训练方案**：专门有 SID Prediction 任务族，通过 MOPD 训练模型生成高质量的 SID

**4. 设计理念总结**

虽然 SID 本身有层级结构，但：
- SID 的生成过程是 LLM 的语义推理过程，不是简单的查表
- 用户意图是自然语言，需要 LLM 进行理解和转换
- 多轮上下文和状态管理需要 LLM 的推理能力
- 多意图协调和权衡是传统索引无法做到的

这正是 ShopX "模型原生履约"范式的核心价值：将商品空间操作统一到模型内部，减少接口信息损失。

### 10.4 是否可以用 LLM 生成前缀后使用工具检索

**核心结论：技术上可行，但不符合 ShopX 的设计理念。**

**1. 符号澄清**

首先需要纠正一个符号问题：在 G₂+L₄ 结构中，前两个 token 是 **z^G_1, z^G_2**（都是全局前缀），而不是 z^G_1, z^L_1。正确的结构是：

```
SID = [z^G_1, z^G_2] + [z^L_1, z^L_2, z^L_3, z^L_4]
       ↑ 全局前缀(2个)     ↑ 局部后缀(4个)
```

**2. 混合检索架构的可行性**

基于前缀的混合检索在生成式检索文献中是存在的（例如 prefix-constrained ANN lookup）：
- LLM 根据用户意图生成全局前缀 `[z^G_1, z^G_2]`
- 工具根据前缀在码本中查找对应的候选商品
- 返回候选商品列表

这种架构在技术上是可行的，并且在某些场景下可能有优势（如降低计算成本）。

**3. ShopX 为什么不采用这种设计？**

这是一个**设计理念的选择**，而不是技术上的不可能：

- **后缀 token 携带细粒度语义信息**：局部后缀（L₄）包含了商品的细粒度属性（颜色、材质、功能等），如果只使用前缀检索，这些信息会丢失，导致检索结果过于宽泛，需要额外的重排序步骤
- **ShopX 的目标是统一履约**：论文的核心目标是实现完整的履约链路（检索+重排序+响应生成+状态更新），如果将检索拆分到工具，就会重新引入接口信息损失，破坏履约链路的统一性
- **完整自回归束搜索的优势**：完整的自回归生成允许模型在相同的上下文理解下，联合优化整个 SID 路径，束搜索可以在整个序列空间中找到最优的 SID 组合

**4. 统一履约 vs 混合检索对比**

| 维度 | ShopX 统一履约 | 混合检索（LLM+工具） |
|------|---------------|---------------------|
| **检索粒度** | 完整 SID（含细粒度属性） | 前缀-only（宽泛类别） |
| **语义一致性** | 前缀和后缀统一生成，语义一致 | 前缀和后缀分开生成，可能不一致 |
| **重排序需求** | 模型内部完成 | 需要额外的重排序步骤 |
| **接口信息损失** | 无 | 有（前缀到工具的转换） |
| **履约链路** | 统一（检索+重排序+响应+状态） | 拆分（检索在工具，其他在模型） |

**5. 重要提醒**

**论文没有明确对比这种混合方法！** 论文只对比了工具中介式基线（InteRecAgent, Chat-REC, RecMind），这些基线使用的是传统的关键词搜索工具，而不是基于 SID 前缀的检索。因此，我们不能说 ShopX 一定优于混合检索，这只是一个设计理念的选择。

**6. 完整的 SID 生成流程**

```
用户意图 → LLM理解 → 自回归生成完整SID序列 → Catalog验证 → 返回真实商品
                          │
                          ├─ z^G_1 (全局前缀第1级)
                          ├─ z^G_2 (全局前缀第2级)
                          ├─ z^L_1 (局部后缀第1级)
                          ├─ z^L_2 (局部后缀第2级)
                          ├─ z^L_3 (局部后缀第3级)
                          └─ z^L_4 (局部后缀第4级)
```

**7. 设计理念总结**

虽然基于 SID 前缀的混合检索在技术上是可行的，但 ShopX 选择了**模型原生履约**的设计理念，让 LLM 完整生成整个 SID 序列。这种设计的优势在于：
- 保持语义一致性
- 支持细粒度属性检索
- 实现统一的履约链路
- 减少接口信息损失

### 10.5 LLM 生成的 SID 是否是全部候选

**核心结论：不是全部满足条件的候选，而是通过束搜索生成的一小部分候选（最多64个）。**

**1. 论文中的关键数据**

- **商品总量**：论文使用了大约 **1.2B（12亿）** 个商品的淘宝快照作为评估的商品宇宙
- **SID 生成数量**：
  - 能力分解实验：使用渐进式束大小调度 `[8, 32, 64, 64, ...]`，**每个查询最多返回64个生成的SID**
  - 框架级评估：使用束大小30进行SID束搜索

**2. 量级对比**

| 维度 | 量级 |
|------|------|
| 商品总量 | 约1.2B（12亿） |
| LLM生成的SID数量 | 最多64个 |
| 每个SID对应的商品数量 | 多个（商品簇） |
| 最终返回给用户的商品数量 | 通常5个以内 |

**3. 重要理解**

**SID 是商品簇的标识符，不是单个商品的标识符。**

论文引入了 **Avg. Item** 指标："the average number of catalog items attached to the beam-search top-1 SID, so lower values mean the generated code path is more specific."

这意味着：
- 一个SID可能对应多个实际商品（同一商品的不同规格、颜色等）
- LLM生成的64个SID候选，实际上代表了64个商品簇
- 通过Catalog验证后，每个SID会映射到多个实际商品
- 最终返回给用户的是经过筛选和重排序后的少量商品

**4. 完整的检索流程**

```
用户意图 → LLM理解 → 束搜索生成64个SID候选 → Catalog验证 → 每个SID映射到多个商品 → 返回真实商品列表
                                     │                          │
                                     ↓                          ↓
                                 最多64个SID              每个SID对应多个商品
                                 （商品簇的代表）         （实际商品）
```

**5. 为什么不是全部候选？**

- **计算效率**：生成全部1.2B商品对应的SID是不可能的，计算量太大
- **束搜索的目的**：束搜索的目的是在有限的计算资源内找到最优的候选，而不是枚举所有可能
- **模型能力限制**：模型只能生成有限数量的候选，需要在质量和数量之间取得平衡
- **后续处理**：生成的SID需要经过Catalog验证和重排序，最终只返回少量高质量商品

### 10.6 SID 的精确范围

**核心结论：平均每个 SID 对应约 14 个商品，是商品簇级别的粒度。**

**1. 论文中的关键指标：Avg. Item**

论文在 SID 设计消融实验中引入了 **Avg. Item** 指标："the average number of catalog items attached to the beam-search top-1 SID, so lower values mean the generated code path is more specific."

在 **25M 商品的 mini catalog** 上的测试结果：

| SID 设计 | Avg. Item（每个SID平均对应商品数） |
|----------|----------------------------------|
| FORGE G3 | 99.1 |
| G EP CL G3 | 256.1 |
| G EP -- G3 | 126.5 |
| G EP -- G6 | 190.7 |
| **G₂+L₄（最终选择）** | **13.8** |

**2. SID 粒度分析**

- **不是单个商品**：一个 SID 对应约14个商品，说明 SID 是**商品簇**的标识符
- **不是宽泛类别**：相比其他设计（99-256个商品），G₂+L₄ 的粒度要细得多
- **具有一定的语义特异性**：能够区分出相当细粒度的商品属性（如颜色、材质、功能等）

**3. SID 粒度的层次结构**

```
商品宇宙（1.2B）
    ↓
商品类别（如：骑行装备）
    ↓
商品子类（如：骑行上衣）
    ↓
商品簇（如：夏季透气骑行上衣，约14个商品） ← SID的粒度
    ↓
单个商品（如：黑色冰丝骑行上衣 M码）
```

**4. 实际应用中的表现**

| 指标 | G₂+L₄ | 说明 |
|------|-------|------|
| **Desc.→Item HR@4** | 2.3 | 从描述到商品的命中率，4个候选中命中的概率 |
| **Desc.→Item HR@64** | 11.3 | 64个候选中命中的概率 |
| **SID→Desc. ROUGE** | 31.5 | 从SID恢复商品描述的质量 |

**5. 总结**

SID 的精确范围是**商品簇级别**，平均每个 SID 对应约 14 个商品。这种设计在以下方面取得了平衡：
- **语义可恢复性**：能够从 SID 中恢复商品的类别、属性等语义信息
- **LLM 可操作性**：6个token的序列适合自回归生成，且前缀结构稳定
- **检索效率**：14个商品的粒度足够细，可以提供多样化的候选，同时又不会过于宽泛

**6. 重要澄清：测试环境的差异**

需要注意的是，Avg. Item = 13.8 和 HR@64 = 11.3% 是在特定测试环境下得到的结果：
- **测试数据**：25M 商品的 mini catalog（不是完整的 1.2B 商品）
- **测试模型**：轻量级 4B 验证模型（不是最终的 8B 模型）
- **测试阶段**：codebook validation 阶段（不是最终框架级评估）

**7. 为什么 HR@64 = 11.3% 看起来很低？**

- **这是 codebook validation 阶段的结果**：目的是评估不同 SID 设计的可学习性，而不是评估最终系统性能
- **完整系统有额外的补偿机制**：通过 Catalog 验证和重排序，可以补偿单个 SID 生成的弱点
- **框架级结果显示更强的端到端性能**：ShopX-8B 在 Item Precision（95.0）和 Ranking Quality（95.5）上表现出色

**8. SID 粒度的实际意义**

无论具体数字如何，SID 的设计理念是明确的：
- **商品簇级别**：一个 SID 对应一组具有相似属性的商品
- **语义可恢复性**：能够从 SID 中恢复商品的类别、属性等信息
- **LLM 可操作性**：适合自回归生成，支持束搜索

这种设计在用户需要多个相似商品进行比较、对属性有要求但对具体型号没有明确要求的场景中特别有用。

### 问题：本文的 SID 如何设计和训练？

**1. 设计目标**

SID 的设计围绕两个核心目标：
- **语义可恢复性**：保留商品语义，使模型能够恢复或推理类别、属性、风格、功能和视觉外观
- **LLM 可操作性**：作为自回归生成目标可学习且稳定，前缀结构避免高熵的下一个 token 选择

**2. 设计流程**

**阶段 1：多模态商品表示学习**
- **编码器**：Qwen3-VL-Embedding-2B，直接处理完整商品输入 `x_i=(v_i,a_i,t_i)`（图片、结构化属性、标题）
- **监督信号**：等价产品监督（EP），正样本是同一商品的不同列表
- **输出结构**：多向量输出（MV），包含全局向量 `g_i` 和多个局部向量 `ℓ_{i,m}`
- **损失函数**：`L_rep = L_CL(R) + λ_TR * L_TR`（对比学习损失 + 文本重建损失）

**阶段 2：混合全局-局部 SID 构建**
- **全局前缀（G₂）**：通过残差量化（RQ）从全局嵌入 `g_i` 生成，提供稳定的自回归路由信号
- **局部后缀（L₄）**：通过向量量化（VQ）从局部嵌入 `ℓ_{i,m}` 生成，保留细粒度属性信息
- **最终结构**：`G₂+L₄`，即 2 个全局前缀 token + 4 个局部后缀 token

**阶段 3：轻量级验证**
- **表示内在指标**：测试连续商品空间是否语义可恢复和邻域稳定
- **全局前缀内在指标**：测试量化是否保留语义结构、前缀稳定性和健康的码本使用
- **轻量级码本验证**：在 25M 商品的 mini catalog 上训练 4B LLM，测试双向语言-商品接地能力

**3. 训练流程**

**阶段 1：SID Token Alignment**
- **目的**：建立自然语言商品语义和 SID token 空间之间的双向接口
- **数据**：目录衍生的商品-to-SID 和 SID-to-商品重建数据
- **训练方式**：冻结所有原始模型参数，只训练新添加的 SID token 嵌入，1 个 epoch，200B 对齐 token

**阶段 2：Domain Continued Pre-training（CPT）**
- **目的**：使模型适应目录-SID 接地、意图和行为条件的商品推理、用户偏好理解和接地生成
- **数据混合**：
  - 购物域数据：约 70B token（目录-SID 接地、意图/行为到商品接地、用户偏好理解）
  - 通用回放数据：约 35B token（知识和推理、指令遵循、数学和编码）
- **训练方式**：更新全模型参数，1 个 epoch，20,480 token 序列长度

**4. 关键设计决策总结**

| 设计维度 | 选择 | 原因 |
|----------|------|------|
| 编码器 | Qwen3-VL-Embedding-2B | 多模态信息可以在 SID 构建前交互 |
| 监督信号 | EP（等价产品） | 更强的语义对齐，避免协作先验 |
| 输出结构 | MV（多向量） | 保留细粒度匹配信号，全局+局部分离 |
| 全局前缀 | 残差量化（RQ） | 提供稳定的自回归路由信号 |
| 局部后缀 | 向量量化（VQ） | 保留细粒度属性信息，不参与残差链 |
| 最终结构 | G₂+L₄ | 平衡语义可恢复性和 LLM 可操作性 |
| Alignment | 冻结主模型，只训练嵌入 | 避免破坏原有语言和推理能力 |
| CPT | 全模型训练 | 适应购物域知识和任务 |

    ↓

    ↓

**6. 重要澄清**

**澄清 1：SID 码本构建是离线预处理步骤**

SID 码本构建（RQ/VQ 量化）是一个**离线预处理步骤**，在任何 LLM 训练开始之前完成：
- 学习码本（codebook）
- 为目录中的所有商品分配 SID
- 这一步与 LLM 无关，只涉及多模态编码器和量化算法
- LLM 学习生成这些预先分配的 SID，而不是凭空创造新的 SID

**澄清 2：Post-training 阶段的关键作用**

Post-training 阶段（SFT + 多教师蒸馏 + RL）是模型真正学会使用 SID 的地方：
- **SFT**：建立广泛的任务覆盖，但提供有限的 SID 生成能力
- **仅 SID 预测训练**：显著提高检索性能，但严重损害通用能力
- **多教师蒸馏（MOPD）**：通过任务族感知的教师路由，同时保留 SID 专业化和恢复通用行为
- **RL 奖励**：进一步优化任务特定性能

论文的消融实验表明：**仅优化 SID 预测会损害更广泛的智能购物能力**，必须通过多教师蒸馏来恢复这些能力。

### 问题：这么看来每个 SID 都是由 6 个 token 组成，推理的时候，根据用户的 Query，LLM 进行理解，然后生成出来是吗？

**核心结论：是的，您的理解完全正确！**

**1. SID 结构**

每个 SID 由 6 个 token 组成（G₂+L₄）：
- `z^G_1`：全局前缀第1级
- `z^G_2`：全局前缀第2级
- `z^L_1`：局部后缀第1级
- `z^L_2`：局部后缀第2级
- `z^L_3`：局部后缀第3级
- `z^L_4`：局部后缀第4级

**2. 推理流程**

根据论文 Section 2 的描述，推理阶段的 SID 生成发生在 **Execute** 动作槽中：

```
用户请求 → Plan（意图理解）→ Execute（SID束搜索）→ Catalog验证 → Fulfill（生成响应）→ Update（状态更新）
```

**3. 自回归生成过程**

模型通过**自回归束搜索**生成完整的 6-token SID 序列：

```
用户意图 → LLM理解 → 自回归生成完整SID序列
                          │
                          ├─ z^G_1 (全局前缀第1级)
                          ├─ z^G_2 (全局前缀第2级)
                          ├─ z^L_1 (局部后缀第1级)
                          ├─ z^L_2 (局部后缀第2级)
                          ├─ z^L_3 (局部后缀第3级)
                          └─ z^L_4 (局部后缀第4级)
```

**4. 束搜索策略**

论文使用**渐进式束大小调度**：

| SID 层级 | 束大小 |
|----------|--------|
| z^G_1 | 8 |
| z^G_2 | 32 |
| z^L_1 | 64 |
| z^L_2 | 64 |
| z^L_3 | 64 |
| z^L_4 | 64 |

- **初期**（全局前缀）使用较小的束大小（8→32），快速收敛到正确的商品类别
- **后期**（局部后缀）使用较大的束大小（64），探索更多细粒度属性组合
- **最终**：每个查询最多返回 64 个生成的 SID 候选

**5. 重要细节**

- **生成的是预定义的 SID**：模型生成的 SID 是预先存在于码本中的预定义 SID，而不是凭空创造新的 SID
- **Catalog 验证**：生成的 SID 候选需要经过 Catalog 验证，确认有效性并映射到真实商品
- **与工具中介式架构对比**：ShopX 直接在模型内部操作商品空间（SID），减少了接口信息损失

**6. 总结**

是的，推理时 LLM 根据用户 Query 理解意图，然后通过自回归束搜索生成完整的 6-token SID 序列。生成的 SID 经过 Catalog 验证后映射到真实商品，最终通过 Fulfill 阶段生成用户响应。

**7. 重要补充说明**

**补充 1：束搜索是树形搜索，不是简单的顺序生成**

束搜索过程实际上是一个**树形搜索**：

```
Level 1 (z^G_1): 生成 8 个候选 → 保留 top-8
                    ↓
Level 2 (z^G_2): 每个候选扩展 → 保留 top-32
                    ↓
Level 3 (z^L_1): 每个候选扩展 → 保留 top-64
                    ↓
Level 4 (z^L_2): 每个候选扩展 → 保留 top-64
                    ↓
Level 5 (z^L_3): 每个候选扩展 → 保留 top-64
                    ↓
Level 6 (z^L_4): 每个候选扩展 → 保留 top-64（最终结果）
```

- **不是**：先生成一个完整的 SID，再生成下一个
- **而是**：在每个层级维护多个部分序列，逐步扩展，最终保留 64 个完整的 SID 候选

**补充 2：理解和生成是统一的，没有独立的理解模块**

理解和生成是统一的自回归解码过程：
- 模型生成 SID token 时，条件是完整的上下文（用户查询、历史记录、状态）
- 理解过程隐含在条件化中，不是一个独立的模块

**补充 3：文本-SID 交错能力**

论文的 Fulfill 阶段提到了 **text-SID interleaving**：
- 模型可以在输出中**交错自然语言和 SID token**
- 例如："为您推荐以下夏季骑行装备：[SID:1024,2048,100,200,500,1000] 这款透气上衣和 [SID:1024,3000,100,300,600,1100] 这款冰丝手套"

**补充 4：多意图查询的处理**

对于多意图查询（如"买骑行上衣和手套"），Execute 槽可以产生 **structured candidate groups**：
- 在一次执行中生成多个 SID 批次
- 每个批次对应不同的商品类别

**8. 更新后的推理流程**

```
用户请求（如："夏天骑车太热了，想买透气的骑行上衣和手套"）
    ↓
Plan（意图理解：识别两个类别需求）
    ↓
Execute（SID束搜索：生成结构化候选组）
    │
    ├─ 骑行上衣 SID 批次（64个候选）
    └─ 骑行手套 SID 批次（64个候选）
    ↓
Catalog验证（映射到真实商品）
    ↓
Fulfill（生成响应，支持文本-SID交错）
    ↓
Update（状态更新）
```

### 问题：介绍 Beam Search 这个过程，比如说"骑行装备"如何得到 1024，1024 如何得到 2048。是模型训练时已经蕴含了这种能力，通过 autoregressive 的方式生成出来？

**核心结论：是的，模型在训练时已经学习了从自然语言意图到 SID 的映射能力，推理时通过自回归束搜索生成完整的 SID 序列。**

**1. 训练过程：模型如何学会生成 SID**

模型通过多阶段训练学会生成 SID：

- **SID Token Alignment**：将 SID 词汇表添加到模型中，只训练新添加的 SID token 嵌入，让模型认识到 SID 是模型可操作的商品标识符
- **Domain CPT**：全模型训练，学习意图到 SID 的映射，包括目录-SID 接地数据和意图/行为到商品接地数据
- **SFT**：监督微调，学习在对话上下文中使用 SID
- **MOPD（多教师蒸馏）**：专门训练 SID Prediction Teacher，强化 SID 生成能力，同时保留通用能力

**2. Beam Search 过程详解（以"骑行装备"为例）**

**输入**：用户查询 "夏天骑车太热了，想买透气的骑行装备"

**Step 1：生成第一个 token z^G_1**
```
输入上下文：用户查询 + 历史记录 + 状态
                    ↓
模型计算条件概率：P(z^G_1 | 上下文)
                    ↓
选择概率最高的 top-8 个候选 token
                    ↓
保留 8 个部分序列：[1024], [1025], [1026], ..., [1031]
```
假设 1024 对应"运动户外"类别。

**Step 2：生成第二个 token z^G_2**
```
对于每个保留的部分序列：
[1024] → P(z^G_2 | 上下文, [1024]) → 选择 top-K 候选
[1025] → P(z^G_2 | 上下文, [1025]) → 选择 top-K 候选
...
                    ↓
从所有扩展序列中选择概率最高的 top-32 个
                    ↓
保留 32 个部分序列：[1024, 2048], [1024, 2049], ...
```
假设 2048 对应"骑行装备"子类。

**Step 3：生成局部后缀 token z^L_1 到 z^L_4**
```
继续生成 z^L_1, z^L_2, z^L_3, z^L_4，每步保留 top-64
                    ↓
最终得到 64 个完整的 SID 序列：
[1024, 2048, 100, 200, 500, 1000]
[1024, 2048, 100, 200, 500, 1001]
...
```

**3. 自回归生成的本质**

模型生成 SID 的过程是条件概率建模：
```
P(SID | 上下文) = P(z^G_1 | 上下文) × P(z^G_2 | 上下文, z^G_1) × ... × P(z^L_4 | 上下文, z^G_1, z^G_2, z^L_1, z^L_2, z^L_3)
```

每个 token 的生成都依赖于：
- 用户查询
- 历史对话记录
- 之前生成的 SID token

**4. 语义几何的作用**

论文提到："The operability of this prefix comes from the semantic geometry learned in Section 4.1"

- 在表示学习阶段，等价产品监督和同类别难负样本组织了全局向量空间
- 残差量化将这个语义空间转换为自回归前缀路径
- 相似的商品在向量空间中距离相近，因此它们的 SID 前缀也相近
- 模型学会了这种语义到 SID 的映射

**7. 重要澄清**

**澄清 1：token ID 是示例，实际码本大小**

之前使用的 token ID（如 1024, 2048, 100 等）是**示例**，实际的码本大小是：
- **vocabulary size 8192 per codebook level**（每个码本级别有 8192 个 token）
- 理论上，G₂+L₄ 的 SID 可以表示 $8192^6$ 种不同的商品簇

**澄清 2：Plan/Execute/Fulfill/Update 是一次解码**

四个动作槽**不是单独的模型调用**：
- 模型在一次自回归解码中生成完整的响应，包括所有四个动作槽的内容
- Harness 负责解析和路由这些输出

**澄清 3：隐藏的推理过程**

论文提到了 **hidden reasoning spans**（隐藏的推理跨度），模型在生成可见的 SID token 之前，会先生成类似 chain-of-thought 的推理过程：
```

[可见输出] [SID:xxx,xxx,xxx,xxx,xxx,xxx] 夏季透气冰丝骑行上衣
```

**澄清 4：训练与推理的一致性**

MOPD 训练时使用的束搜索与推理时一致：
> "SID Prediction rollouts use six-level SID generation with beam search."

这确保了训练和推理的一致性，避免了训练-测试偏差。

### 问题：Fulfill 过程有进行生成的 SID 排序吗？

**核心结论：排序主要发生在 Execute 阶段，但 Fulfill 阶段也可能进行最终的排序调整。**

**1. Execute 阶段负责检索和重排序**

根据论文 Section 2 的描述，Execute 阶段的输出明确包括：
> "a selected, reranked, compared, or bundled set of catalog-grounded items"

在 Intent-to-Item Fulfillment 的流程图中，Execute 阶段标注为 **"retrieval & rerank"**。

**2. Fulfill 阶段负责生成用户响应**

Fulfill 阶段的输入包括：
> "fulfillment plan, selected items, resolved Catalog evidence, assembled Context or State, and user-facing constraints"

输出包括：
> "a recommendation list, product comparison, grounded summary, bundle presentation, text--SID interleaved answer, direct contextual response, or clarification question"

**3. 排序是一个单独的任务族**

在 post-training 阶段，有专门的 **Ranking reward**：
> "For listwise ranking tasks, the model is provided with a set of candidate items and is required to output a ranked permutation according to their relevance to the given user intent."

排序任务使用 NDCG-based reward，是五个任务族之一（General, SID Prediction, Ranking, Interleave, Other）。

**4. 完整的排序流程**

```
用户请求
    ↓
Plan → 意图理解，确定需要排序
    ↓
Execute → SID束搜索检索 + Catalog验证 + 初步重排序
    │
    ├─ 束搜索生成64个SID候选（本身有概率排序）
    ├─ Catalog验证映射到真实商品
    └─ 模型根据意图进行初步排序（rerank）
    ↓
Fulfill → 最终排序调整 + 生成用户响应
    │
    ├─ 根据上下文和用户偏好进行最终排序调整
    ├─ 选择要展示的商品数量（通常5个以内）
    └─ 生成包含排序结果的用户响应
    ↓
Update → 状态更新
```

**5. 排序是隐含在自回归生成中的**

由于四个动作槽在一次自回归解码中完成，排序不是一个单独的步骤，而是**隐含在模型生成 SID token 的顺序中**：
- 模型在 Execute 阶段生成 SID 时，已经按照相关性排序
- 第一个生成的 SID 是最相关的，第二个次之，依此类推
- Fulfill 阶段只是按照这个顺序展示结果

**6. Ranking 任务族是训练时的任务格式**

需要区分训练时的 Ranking 任务族和推理时的排序行为：
- **训练时**：Ranking 任务族是五个任务族之一，使用 NDCG-based reward 优化排序性能
- **推理时**：排序是 Execute 阶段的一部分，通过自回归生成完成

**7. 训练中的排序优化**

模型在训练时通过多种方式学习排序能力：
- **Domain CPT**：意图/行为到商品接地数据包括排序相关的训练样本
- **SFT**：购物数据中包含排序相关的监督信号
- **MOPD**：专门的 Ranking reward 使用 NDCG-based reward 优化排序性能

**8. 总结**

**排序主要发生在 Execute 阶段，Fulfill 阶段不进行排序。**

具体来说：
- **Execute 阶段**：负责 SID 束搜索检索、Catalog 验证和重排序，排序隐含在模型生成 SID 的顺序中
- **Fulfill 阶段**：负责展示已经排序的结果，将排序后的商品转化为用户可见的响应
- **训练阶段**：通过专门的 Ranking reward（NDCG-based）优化排序性能

### 问题：SID 和 Catalog-grounded 的对应在哪里得到保证？如何训练？

**核心结论：SID 和 Catalog 的对应关系通过离线预处理、训练阶段和推理阶段三个层面得到保证。**

**1. 离线预处理阶段：建立 SID-Catalog 对应关系**

**步骤 1：多模态商品表示学习**
```
商品输入 x_i = (图片 v_i, 属性 a_i, 标题 t_i)
                    ↓
Qwen3-VL-Embedding-2B 编码器 E_θ
                    ↓
连续表示 (全局向量 g_i, 局部向量 ℓ_i,1, ..., ℓ_i,M)
```

**步骤 2：量化生成 SID**
```
全局向量 g_i → 残差量化 (RQ) → 全局前缀 G₂ = (z^G_1, z^G_2)
局部向量 ℓ_i,m → 向量量化 (VQ) → 局部后缀 L₄ = (z^L_1, z^L_2, z^L_3, z^L_4)
                    ↓
完整 SID = G₂ + L₄ = (z^G_1, z^G_2, z^L_1, z^L_2, z^L_3, z^L_4)
```

**关键机制**：
- **量化过程是多对一映射**：相似的商品（等价产品、同类商品）在向量空间中距离相近，量化后会分配到相同的 SID
- **平均每个 SID 对应约 13.8 个商品**（Avg. Item = 13.8）
- **映射关系存储在 Catalog 中**：每个 SID 对应的商品列表存储在 Catalog 中

**2. 训练阶段：学习 SID 和商品的对应关系**

**CPT 阶段**：

### 问题：SID 和商品的映射怎么得到的？是离线预处理对 SID 和商品进行分配？

**核心结论：是的，SID 和商品的映射是通过离线预处理得到的，具体包括码本训练和商品到 SID 的分配两个阶段。**

**1. 离线预处理的两个阶段**

**阶段 1：码本训练（学习量化器）**

```
训练集商品 → 多模态编码器 → 连续表示 → 训练码本（量化器）
```

这个阶段训练两个部分：
- **多模态编码器 E_θ**：将商品输入（图片、属性、标题）编码为连续向量
- **码本（量化器）**：学习如何将连续向量映射到离散的 SID token

**训练过程**：
1. 使用等价产品监督（EP）训练编码器，让相似的商品在向量空间中距离相近
2. 使用残差量化（RQ）训练全局前缀码本，使用向量量化（VQ）训练局部后缀码本
3. 通过重建损失确保量化后的向量能够重建原始向量

**阶段 2：商品到 SID 的分配**

```
全量商品 → 多模态编码器 → 连续表示 → 量化 → SID → 存储到 Catalog
```

**全局前缀分配**：
```
z^G_{i,k} = argmin_{c} ||r_{i,k-1} - e^G_{k,c}||_2^2
r_{i,k} = r_{i,k-1} - e^G_{k,z^G_{i,k}}
```

**局部后缀分配**：
```
z^L_{i,m} = argmin_{c} ||ℓ_{i,m} - e^L_{m,c}||_2^2
```

**2. 完整的离线预处理流程**

```
┌─────────────────────────────────────────────────────────┐
│ 阶段 1：码本训练（学习量化器）                            │
│                                                         │
│ 训练集商品（图片、属性、标题）                              │
│     ↓                                                   │
│ Qwen3-VL-Embedding-2B 编码器 E_θ（训练中）                │
│     ↓                                                   │
│ 连续表示（全局向量 g_i, 局部向量 ℓ_i,m）                  │
│     ↓                                                   │
│ 等价产品监督 + 重建损失（训练编码器）                      │
│     ↓                                                   │
│ 残差量化（RQ）训练全局前缀码本 C^G_k                     │
│ 向量量化（VQ）训练局部后缀码本 C^L_m                     │
│     ↓                                                   │
│ 得到训练好的编码器 E_θ 和码本 C^G_k, C^L_m               │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 阶段 2：商品到 SID 的分配（对全量商品）                    │
│                                                         │
│ 全量商品（约1.2B）                                       │
│     ↓                                                   │
│ 训练好的编码器 E_θ（冻结）                                │
│     ↓                                                   │
│ 连续表示（全局向量 g_i, 局部向量 ℓ_i,m）                  │
│     ↓                                                   │
│ 量化：                                                   │
│ - 全局前缀：g_i → (z^G_1, z^G_2) 通过 RQ                │
│ - 局部后缀：ℓ_i,m → (z^L_1, z^L_2, z^L_3, z^L_4) 通过 VQ│
│     ↓                                                   │
│ 完整 SID = G₂ + L₄ = (z^G_1, z^G_2, z^L_1, z^L_2, z^L_3, z^L_4)
│     ↓                                                   │
│ 将 SID-商品列表映射关系存储到 Catalog                     │
└─────────────────────────────────────────────────────────┘
```

**3. 为什么是多对一映射？**

- 码本中的码字数量是有限的（每个级别 8192 个）
- 而商品数量是巨大的（约 1.2B）
- 量化过程会将相似的向量分配到同一个码字
- 因此，相似的商品会分配到相同的 SID
- 平均每个 SID 对应约 13.8 个商品（Avg. Item = 13.8）

**4. Catalog 的数据结构**

- **SID → 商品列表**：一个 SID 对应多个商品
- **商品 → SID**：一个商品对应唯一的 SID（反向索引，用于训练数据生成）

**5. 训练数据的生成**

CPT 阶段的 Catalog--SID Grounding 数据是通过离线预处理生成的：
1. 遍历全量商品
2. 对每个商品提取标题/详情
3. 查询 Catalog 得到对应的 SID
4. 生成训练样本

**6. 总结**

SID 和商品的映射是通过离线预处理得到的：
1. **码本训练阶段**：训练编码器和量化器，学习如何将商品编码为连续向量并量化为离散 SID
2. **商品分配阶段**：对全量商品进行量化，得到每个商品的 SID，存储到 Catalog 中
3. **多对一映射**：相似的商品会分配到相同的 SID（平均每个 SID 对应约 13.8 个商品）
4. **推理阶段**：通过 Catalog 查询 SID 对应的商品列表

**2. 为什么量化过程与 LLM 训练分离？**

**技术原因**：
- **不同的训练目标**：量化过程的目标是学习商品的语义表示和离散编码，而 LLM 训练的目标是学习语言理解和生成能力
- **不同的训练方法**：量化过程使用对比学习和重建损失，而 LLM 训练使用自回归语言建模损失
- **计算效率**：量化过程可以在较小的数据集上进行，而 LLM 训练需要大量的计算资源

**设计原因**：
- **模块化设计**：将商品表示学习与 LLM 训练分离，使得两者可以独立优化
- **可复用性**：训练好的码本可以应用于不同的 LLM 架构
- **稳定性**：固定的码本可以保证训练和推理的一致性

**3. LLM 训练如何使用固定的码本？**

- **SID Token Alignment**：将码本中的所有 SID token 添加到 LLM 的词表中，只训练新添加的 SID token 嵌入
- **Domain CPT**：使用基于固定码本生成的 Catalog--SID Grounding 数据和 Intent/Behavior-to-Item Grounding 数据
- **SFT**：使用基于固定码本生成的 SID-Native Fulfillment 数据
- **OPD-RL**：通过在固定码本上训练的 SID Prediction Teacher 强化 SID 生成能力

**4. 关键证据**

论文中的描述：
> "After SID token alignment and domain continued pre-training establish a SID-aware foundation model, post-training teaches the model to follow the framework action protocol..."

这表明 SID 码本在这些阶段之前已经固定。

> "We build on FORGE, a collaborative-heavy SID construction framework developed for industrial generative retrieval..."

这表明 SID 构建是基于 FORGE 框架的，与 LLM 训练分离。

**5. 总结**

量化过程与 LLM 训练是分离的：
1. **离线预处理阶段**：训练编码器和码本，对全量商品进行量化分配 SID，得到固定的码本和 SID-商品映射
2. **LLM 训练阶段**：使用固定的码本和映射进行训练，包括 SID Token Alignment、Domain CPT、SFT、OPD-RL
3. **分离的原因**：不同的训练目标、不同的训练方法、模块化设计、可复用性、稳定性
