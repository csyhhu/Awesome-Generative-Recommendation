## 0. 综合理解与点评

### 用户综合理解

> 本文中心思想是 Teacher 模型训练全部的 tokens, student 模型使用 Token Merge 的方式学习，然后提出了三种 Merge 策略。其中加速效果最明显的 PATM 其实就是分段，然后不同段内按不同的 step 进行 sum pooling 压缩。

### 点评：方向正确，细节需补充

**✅ 大方向完全正确**，抓住了论文的两个核心：
1. **Teacher-Student 分工**：教师保留全部 Token，学生用 Token Merge 压缩
2. **PATM 的本质**：分段 + 不同压缩 step 的 Sum Pooling，且确实是单策略中加速最明显的


#### 补充：PATM 的分段原则需明确

用户说"不同段内按不同 step 压缩"是准确的，但需补充分段原则：
- **近期 Token 少压缩**（如最新 3K 段 K=1，不压缩）
- **历史 Token 多压缩**（如最远 10K 段 K=4）
- 这一原则来自注意力分布分析：**最新 10% 的 Token 贡献约一半的注意力权重**
- 最终选择配置：3K:1, 5K:2, 10K:3, 20K:4（中间方案，平衡性能与延迟）

### 完整的修正表述

> 本文中心思想是：师生都使用 Full Attention 建模超长序列；**Teacher 一次性训练全部 20K Token 且不参与线上推理**，Student 通过三种 Token Merge 策略（LITM/PATM/LPTM）压缩序列高效训练与推理，再通过 **KD 从 Teacher 蒸馏知识恢复性能**。其中 PATM 是单策略中加速最明显的（吞吐 +2.09×），其本质是按"近期少压缩、历史多压缩"原则分段，各段用不同 step 进行 Sum Pooling 压缩。

## 1. 研究背景与动机

随着用户行为序列长度的增长（例如从 5K 扩展到 20K），传统推荐系统面临**训练效率和服务吞吐量**的急剧下降。在 ByteDance 的实际广告推荐场景中，序列长度从 5K 增至 20K 后：

- 训练时间增加 **3.5 倍**
- GPU 显存增加 **49GB**
- 服务延迟增加约 **6.3 倍**

现有解决方案主要分为两类：
1. **序列长度压缩**：基于搜索（如 TWIN、SIM）或聚类（如 HiSAC），但会丢失细粒度信息
2. **轻量注意力架构**：如 Target Attention、STCA 等，但无法充分捕捉序列内的依赖关系

**核心矛盾**：有效性（充分建模超长序列）与 效率（训练和推理开销）之间的权衡。

## 2. 关键观察与设计选择

### 2.1 Full Attention (FA) vs Target Attention (TA)

论文通过实验验证了 **Full Attention 优于 Target Attention**：

| 维度 | FA 优势 |
|------|---------|
| AUC | 在 20K 序列上最高提升 **0.25%** |
| 建模能力 | FA 在 5K 上的表现超过 TA 在 20K 上的表现 |
| GPU 利用率 | FA 具有更高的 GPU 利用率 |
| 序列-序列交互 | FA 捕获的 seq-seq 注意力包含重要预测信息 |

### 2.2 注意力分数分布分析

通过对 FA 机制下注意力分数的统计分析，得出三个关键发现，直接启发了后续的 Token Merge 策略：

1. **相同 Product ID 的 Token 注意力分数更接近** → 可按 ID 合并
2. **最新 10% 的 Token 贡献了约一半的注意力权重** → 应按位置自适应合并
3. **底层注意力分布均匀，高层注意力更集中** → 可按层级渐进式合并

## 3. 方法框架

### 3.1 整体架构：两阶段知识蒸馏框架

```
┌─────────────────────────────────────────────────┐
│              Teacher Model (一次性训练)           │
│   • 完整 20K Tokens, 无任何压缩                  │
│   • Full Attention                              │
│   • 缓存预测 Logits 用于蒸馏                     │
└──────────────────────┬──────────────────────────┘
                       │ 知识蒸馏 (KD Loss)
                       ▼
┌─────────────────────────────────────────────────┐
│              Student Model (在线部署)             │
│   • 三种 Token Merge 策略压缩序列                 │
│   • Full Attention                              │
│   • 高效训练与推理                               │
└─────────────────────────────────────────────────┘
```

**核心思想**：将繁重的计算卸载给**仅训练一次、无需线上推理**的 Teacher 模型，Student 模型通过 Token Merge 高效压缩序列，并从 Teacher 中蒸馏知识。

---

### 3.2 Student 模型的三种 Token Merge 策略

#### (1) Local-wise ID-based Token Merge (LITM)

**思想**：用户在短时间窗口内可能多次与同一商品交互，按 Product ID 局部合并这些 Token。

**算法流程**：
```
输入: 序列嵌入 E, Product ID 列表 p, 最大间隔阈值 T
输出: 合并后的序列
1. 遍历每个 Token:
   - 若该 ID 不存在 或 距上次出现位置 > T: 新增 Token
   - 否则: 将当前 Token 合并到已有同 ID Token (Sum Pooling)
```

**工程实现细节**：
- 固定 `T=3`，在局部窗口内聚合相同 ID 的连续交互
- 在 CPU 端合并**原始特征**（而非 Embedding），减少 CPU-GPU 通信开销
- 效果：平均序列长度压缩约 **43%**，AUC 仅下降 **0.02%**

#### (2) Position-wise Adaptive Token Merge (PATM)

**思想**：近期 Token 重要性更高，采用**不同位置差异化压缩强度**。

**算法流程**：
```
输入: 序列 E, 分段数 B, 分段范围 R, 各段压缩因子 K
1. 将序列按位置分为 B 段
2. 对每段 b, 按压缩因子 K_b 合并连续 K_b 个 Token (Sum Pooling)
   - 近期 Token: K=1 (不压缩)
   - 历史 Token: K=2,3,4 (更激进地压缩)
```

**典型配置**（L=20K, B=4）：
- 第1段 [1, 3000]: K=1 → 保留最新 3K Token
- 第2段 [3001, 8000]: K=2 → 压缩为 2.5K
- 第3段 [8001, 13000]: K=3 → 压缩为 ~1.7K
- 第4段 [13001, 20000]: K=4 → 压缩为 ~1.75K
- **合并后总长度约 ~8.9K → 再配合 LITM 可进一步压缩**

#### (3) Layer-wise Pyramid Token Merge (LPTM)

**思想**：底层注意力分布均匀需长序列，高层注意力集中可短序列，形成金字塔结构。

**算法流程**：
```
对 6 层 Transformer:
  Layer 0-1: 处理完整序列长度 L
  Layer 1后: Merge 减半 (每2个Token合并为1个)
  Layer 2-3: 处理长度 L/2
  Layer 3后: Merge 减半
  Layer 4-5: 处理长度 L/4
```

**实现细节**：
- 每 2 层执行一次长度减半操作（Sum Pooling）
- **仅对历史序列 Token 合并，Target Candidate Token 永不合并**
- 在 GPU 上通过 Tensor 操作高效实现

---

### 3.3 Teacher 模型与知识蒸馏

**Teacher 模型**：
- 完整保留 20K 序列 Tokens，不做任何压缩
- 仅训练一次，无需线上部署
- 预测 Logits 缓存用于蒸馏

**Student 损失函数**（双塔结构）：

```
Main Tower:           ℓ_main = BCE(q_S_main, y)
Distillation Tower:   ℓ_dis  = BCE(q_S_dis, y) + λ * BCE(q_S_dis, q_T)
Total Loss:           ℓ      = ℓ_main + ℓ_dis
```

- `λ=50` 时最优：此时蒸馏损失 `λ*ℓ_kd` 与 CE 损失量级相当
- 后期可移除 KD Loss，Student 已充分吸收 Teacher 知识

---

### 3.4 其他工程优化

1. **Stack Sequence**：解决 Batch 内序列长度不均的显存浪费
   - 将所有有效 Token 重新均匀分配到 Batch 各样本
   - 在 GPU 上通过记录的 Token 数量重建
   - **20K 序列可节省高达 10GB GPU 显存**

2. **QK Norm**：在 Attention 计算前对 Query 和 Key 做归一化
   - 解决超长序列 + KD Loss 导致的训练不稳定问题
   - 虽略微增加显存和计算，但有效避免训练发散

## 4. 实验结果

### 4.1 离线整体性能对比

| 方法 | MaxLen | AvgL | ΔAUC | ΔLogLoss | 吞吐 (Thr) | 显存 (Mem) |
|------|--------|------|------|----------|------------|------------|
| Base (5K) | 5K | 1.2K | -- | -- | 88K | 52G |
| LONGER (20K) | 20K | 4.4K | +0.11% | -0.21% | 48K | 70G |
| HyFormer (20K) | 20K | 4.4K | +0.12% | -0.23% | 36K | 75G |
| **TM20K-T (Teacher)** | **20K** | **8.8K** | **+0.26%** | **-0.55%** | **11K** | **86G** |
| TM20K-S (Student) | 20K | 1.8K | +0.15% | -0.29% | 83K | 74G |
| **TM20K-S w/ KD** | **20K** | **1.8K** | **+0.22%** | **-0.43%** | **83K** | **74G** |

**关键结论**：
- TM20K-S + KD 恢复了 Teacher 约 **85%** 的性能增益
- 吞吐仅从基线 88K 降至 83K（下降 ~5%），远优于其他方法
- 平均序列长度从 8.8K 压缩至 1.8K，压缩比高达 **5:1**

### 4.2 Token Merge 消融实验

| 策略组合 | AvgL | P90L | ΔAUC (vs 20K Full) | 吞吐 |
|----------|------|------|---------------------|------|
| 20K Full | 8.8K | 20K | -- | 11K |
| +LITM | 5K | 11.3K | -0.02% | 25K |
| +PATM | 4.5K | 10.2K | -0.06% | 34K |
| +LPTM | 8.8K | 20K | -0.03% | 19K |
| **+LITM + PATM + LPTM** | **1.8K** | **2.6K** | **-0.11%** | **83K** |

对比随机丢弃 40% Token（RandDrop/RandTrunc）：AUC 下降 ~0.1%，说明本文的有动机合并策略在同等压缩比下信息损失更小。

### 4.3 在线 A/B 测试结果

在字节跳动实际广告推荐系统中部署：
- 流量：10% 总流量，持续 5 天，服务数亿用户
- 基线：已长期线上运行的 5K 序列高性能排序模型

| 模型 | ADSS 提升 | ADVV 提升 | 服务延迟增加 |

| TM20K-S | +0.881% | +0.515% | +5.6% |

- P-value 均 < 0.004，统计显著
- Teacher 模型已部署 **8 个月**，为数十个 Student 变体提供蒸馏信号，**至今未重训**
- 年重训成本在所有训练计划摊销后可忽略不计

## 5. 优势与局限

### 优势
1. **易实现**：三种 Token Merge 策略均为规则驱动，工程实现简单
2. **不丢弃 Token**：区别于搜索或长度外推方法，Teacher/Student 均保留全部信息
3. **工业级验证**：在大规模推荐系统中验证了两阶段蒸馏框架的有效性，ADSS +1.036%，延迟仅 +5.6%

### 局限
1. **规则驱动**：Token Merge 方案依赖人工调参，跨域部署需额外适配
2. **未结合稀疏注意力**：稀疏注意力（如 UltraHSTU）与现有优化（User-Level Training、Remove-Padding、FlashAttention）兼容需大量定制化 GPU 算子开发，留作未来工作

---

## 6. 总结

TM20K 通过**两阶段知识蒸馏框架**实现了超长序列建模的有效性与效率平衡：
- **Teacher**：保留完整 20K Token，一次性训练，提供高质量蒸馏信号
- **Student**：通过 LITM（按ID合并）、PATM（按位置自适应合并）、LPTM（层级金字塔合并）三种策略高效压缩序列
- **效果**：电商行为序列从 5K 扩展到 20K，ADSS 显著提升 +1.036%，线上服务延迟仅增加 5.6%

该方案已成功部署于字节跳动电商广告推荐系统，为工业级超长序列推荐提供了可落地方案。

## 7. 讨论记录

### Q1: TM20K 的蒸馏架构与 Rec-Distill 有什么区别？

两篇论文均来自字节跳动同一团队（作者有重叠），都采用"教师-学生 + 双塔 + Logits 蒸馏"的范式，但**核心定位和优化维度有本质区别**。

#### 7.1 蒸馏目的不同（最核心区别）

| 维度 | TM20K | Rec-Distill |
|------|-------|-------------|
| **要解决的问题** | 超长序列建模的**效率问题** | 模型 Scaling 的**成本问题** |
| **教师"重"在哪里** | 重在**计算负载**（20K Full Attention） | 重在**参数规模**（24B 稠密参数） |
| **学生"轻"在哪里** | 轻在**序列长度**（20K→1.8K via Token Merge） | 轻在**参数量**（24B→1B） |
| **KD 转移的是什么** | "完整序列信息"的建模能力 | "大规模参数"的表征能力 |

**一句话总结**：TM20K 是"序列长度维度的卸载"，Rec-Distill 是"参数规模维度的压缩"。

#### 7.2 教师模型策略差异

| 维度 | TM20K | Rec-Distill |
|------|-------|-------------|
| **教师更新频率** | 一次性训练，已部署 8 个月未重训 | Batch + Streaming 持续更新 |
| **教师是否上线** | ❌ 完全离线，仅缓存 Logits | ❌ 离线，但需流式写入存储 |
| **退化风险** | 低（电商序列分布相对稳定） | 高（流式数据下教师不更新会迅速退化） |
| **训练数据扩展** | 未提及，固定训练集 | 遵循 Chinchilla scaling law 同比例扩展 |

#### 7.3 学生双塔设计的微妙差异

**TM20K 的双塔**：
```
Main Tower:         ℓ_main = BCE(q_S_main, y)            ← 仅 ground-truth
Distillation Tower: ℓ_dis  = BCE(q_S_dis, y) + λ·KD       ← ground-truth + KD
```
两个 Tower 都用 ground-truth label 训练，Distillation Tower 额外接收 KD 信号，**没有强调故障隔离**。

**Rec-Distill 的 Decoupled-Tower**：
```
Main Tower:      ℓ_task                       ← 仅 ground-truth, 线上推理用
Auxiliary Tower: ℓ_task + α·ℓ_distill        ← ground-truth + KD, 仅训练用
```
**关键差异**：Main Tower 完全隔离，不受教师更新延迟或蒸馏管线故障影响，**强调工业级稳定性**。

#### 7.5 KD Loss 形式

| 维度 | TM20K | Rec-Distill |
|------|-------|-------------|
| **Loss 形式** | BCE-style（教师 logit 当 soft label） | CE-style（更高梯度效率） |
| **权重调优** | λ=50（使 λ·ℓ_kd 与 ℓ_ce 量级相当） | 放松权重和为 1 约束，调参使两者量级匹配 |
| **后期策略** | 训练后期可移除 KD Loss | 持续 Streaming 蒸馏 |

#### 7.6 压缩比与转移率对比

| 指标 | TM20K | Rec-Distill |
|------|-------|-------------|
| **压缩维度** | 序列长度 8.8K → 1.8K（~5x） | 参数量 24B → 1B（24x） |
| **转移率 η** | 约 **85%**（AUC +0.22% / +0.26%） | **45%~64%**（不同场景） |
| **绝对增益** | AUC +0.22%, ADSS +1.036% | AUC +0.44%, ADSS +1.10% |

**TM20K 转移率（85%）显著高于 Rec-Distill（最高 64%）**，原因推测：
- TM20K 师生架构相同（仅序列长度不同），信息迁移更容易
- Rec-Distill 师生参数量差距巨大（24x），容量差距阻碍知识迁移

#### 7.7 适用场景

- **TM20K**：单一场景验证（电商广告 CVR 预测），针对性强
- **Rec-Distill**：多场景验证（电商广告、多场景推荐、TikTok 直播），通用性强，还支持跨阶段蒸馏（精排→粗排）

#### 7.8 何时用哪种？是否可以组合？

- **若瓶颈是"序列长度扩展导致效率下降"** → 选 TM20K 范式：用 Token Merge + 教师卸载 Full Attention 计算
- **若瓶颈是"参数 Scaling 成本高"** → 选 Rec-Distill 范式：用大教师 + Decoupled-Tower + Debias 实现参数压缩

**两者甚至可以互补使用**：教师可以是 Rec-Distill 式的 24B + 20K 大模型，学生采用 TM20K 的 Token Merge 策略压缩序列，再通过 Decoupled-Tower + Debias 蒸馏——这可能是字节跳动内部的实际组合方案（两篇论文作者有重叠，来自同一团队）。

### Q2: 哪种 Token Merge 方式最佳？分别之间的实验效果如何？

#### 7.9 单策略效果对比（基于 20K Full 基线）

| 策略 | AvgL | P90L | ΔAUC | 吞吐 (Thr) | 吞吐提升 | 压缩率 |
|------|------|------|------|-----------|----------|--------|
| 20K Full (基线) | 8.8K | 20K | -- | 11K | -- | -- |
| **+LITM** | 5K | 11.3K | **-0.02%** | 25K | +1.27× | -43% |
| **+PATM** | 4.5K | 10.2K | -0.06% | **34K** | **+2.09×** | **-49%** |
| **+LPTM** | 8.8K | 20K | -0.03% | 19K | +0.73× | 0%（仅中间层） |

#### 7.10 三种策略的特性分析

**LITM（按 ID 合并）—— 性能保持最佳**
- ✅ AUC 损失最小（-0.02%），近乎无损
- ✅ 平均序列长度压缩 43%
- ⚠️ 吞吐提升相对温和（+1.27×）
- **适用场景**：对性能损失敏感、需要稳健压缩的场景

**PATM（位置自适应合并）—— 效率提升最强**
- ✅ 吞吐提升最显著（+2.09×，3倍于基线）
- ✅ 序列压缩最激进（-49%）
- ⚠️ AUC 损失略大（-0.06%）
- **适用场景**：对延迟/吞吐敏感，可容忍小幅度性能损失

**LPTM（层级金字塔合并）—— 中间层压缩特化**
- ✅ AUC 损失小（-0.03%）
- ⚠️ **不改变输入序列长度**（AvgL/P90L 都不变）
- ✅ 通过降低 Transformer 中间层计算量提速
- **本质**：与 LITM/PATM 是**互补关系**，不能单独构成完整压缩方案

#### 7.11 组合策略效果

| 组合 | AvgL | P90L | ΔAUC | 吞吐 |
|------|------|------|------|------|
| 20K Full | 8.8K | 20K | -- | 11K |
| LITM + PATM | 1.8K | 2.6K | -0.07% | 68K |
| **LITM + PATM + LPTM** | **1.8K** | **2.6K** | **-0.11%** | **83K** |

**关键观察**：
- LITM+PATM 把序列压到 1.8K（压缩 80%），AUC 仅 -0.07%
- 加入 LPTM 后，**序列长度不变**（仍是 1.8K），但**吞吐从 68K 跃升到 83K**（+22%）
- 这印证了 LPTM 的本质作用：**在 LITM+PATM 已压缩的输入序列基础上，进一步压缩 Transformer 中间层**

#### 7.12 超参数调优

**LITM 的间隔阈值 T**：

| T | ΔAvgLen | ΔAUC |
|---|---------|------|
| T=1 | -39% | -0.02% |
| **T=3**（最终选择） | **-43%** | **-0.02%** |
| T=10 | -57% | -0.04% |

→ T=3 是最佳平衡点：相比 T=1 额外压缩 4% 长度但 AUC 不变；T=10 虽压缩更多但性能下降明显

**PATM 的分段配置**：

| 配置 | ΔAvgLen | ΔAUC |
|------|---------|------|
| 2K:1,4K:2,8K:3,20K:4（最激进） | -55% | -0.09% |
| **3K:1,5K:2,10K:3,20K:4**（最终选择） | **-49%** | **-0.06%** |
| 4K:1,8K:2,12K:3,20K:4（最保守） | -40% | -0.05% |

→ 论文选择中间配置，**优先控制线上延迟在可接受范围**，即使牺牲小幅 AUC

#### 7.13 与随机策略对比（验证有动机合并的必要性）

| 策略 | AvgL | ΔAUC |
|------|------|------|
| RandDrop（随机丢弃 40%） | 5.3K | -0.11% |
| RandTrunc（随机截断） | 5.3K | -0.10% |
| LITM（同长度量级） | 5K | **-0.02%** |

→ 同等压缩比下，**有动机的 LITM 比随机策略性能损失小 5 倍**，验证了基于注意力分布分析的设计合理性

#### 7.14 结论：哪种最佳？

**没有单一"最佳"策略，必须按目标分情况讨论**：

1. **若只选一种 → PATM**：单策略效率提升最大（吞吐 3×），性能损失可接受
2. **若追求最小性能损失 → LITM**：AUC 几乎无损（-0.02%）
3. **若用于工业部署 → 三者级联（最终方案）**：LITM+PATM+LPTM 组合，序列从 8.8K 压到 1.8K，吞吐 83K（接近 5K 基线的 88K），再配合 KD 恢复 85% 性能增益

**设计哲学**：三种策略**各司其职、互补而非替代**——
- LITM 去重（局部同 ID 聚合）
- PATM 时间维度压缩（近期保细、历史合并）
- LPTM 层级维度压缩（底层长、高层短）

三者从**不同维度**共同压缩序列，这也是为什么组合后能达到 80% 压缩比而 AUC 仅损失 0.11% 的关键。
